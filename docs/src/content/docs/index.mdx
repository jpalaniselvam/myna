## Why myna?

Modern serverless systems are built from events, queues, and functions—not just HTTP endpoints. Yet, most developer tools are still API-first. `myna` bridges this gap by providing a repeatable, Git-friendly way to interact with AWS services.

## Define it. Run it. Replay it.

`myna` makes complex AWS interactions feel like simple local scripts.

<Tabs>
  <TabItem label="Lambda">
    <Zap slot="icon" size={16} />
    ```toml
    # invoke-handler.toml
    kind = "lambda.invoke"

    [lambda]
    function_name = "process-order"

    [payload]
    data = '{ "order_id": "123", "status": "PENDING" }'
    ```
  </TabItem>
  <TabItem label="SQS">
    <MessageSquare slot="icon" size={16} />
    ```toml
    # send-message.toml
    kind = "sqs.send"

    [sqs]
    queue_url = "https://sqs.us-east-1.amazonaws.com/123456789012/my-queue"

    [payload]
    data = "New order received"
    ```
  </TabItem>
  <TabItem label="EventBridge">
    <Share2 slot="icon" size={16} />
    ```toml
    # put-event.toml
    kind = "eventbridge.put"

    [eventbridge]
    event_bus_name = "default"
    source = "my.app"
    detail_type = "OrderCreated"

    [payload]
    data = '{ "id": "99" }'
    ```
  </TabItem>
</Tabs>

## How it Works

Setting up a robust testing workflow only takes three steps.

<Steps>
1. **Create a Collection**
   Initialize a directory with a `myna.toml` to manage your shared variables and environments.

2. **Define Your Actions**
   Write simple TOML files for each AWS interaction. Use `{{variable}}` syntax to keep them dynamic.

3. **Execute Anywhere**
   Run actions from your terminal, integrate them into CI/CD, or share them with your team via Git.
</Steps>
